# Audit of 2026-11-09

Four independent read-only reviewers, run on the user's request after the security fixes and the
refactor of SF-123..SF-156: a sandbox-escape reviewer (with live experiments in a lab sandbox
against fake secrets), the attack surfaces outside the sandbox, the code after the refactor, and
reliability and process (including the incidents of the same day). Main at c4f6d33. This file
keeps their joint conclusion and what came of it; names of people, machines and other workspaces
are left out.

## Conclusion

The HTTP surfaces, the Git rules and the secret files held. The sandbox did not: code inside a job
can still leave a trap that the factory or the next Claude session runs outside the sandbox. The
refactor made the code safer to change, but the structure underneath is still tangled, and the
merged code is never the code that was tested.

### 1. Sandbox: fix before more work (the queue was held)

- **Critical, proven in the lab: the test run rewrites the worktree's `.git`.** The test sandbox
  binds the whole worktree writable, `.git` included. A test command pointed `.git` at a git dir
  it created, with a `filter.<x>.clean` command; the factory's next Git call at Clean (no
  sandbox) ran that command as the user.
- **Critical, from the code: agent configuration in the worktree.** The test run, and the
  Implementer's Write and Edit tools (the file guard allows them there), can create
  `.claude/settings.json` with hooks, `.mcp.json` or `.codex/` config. The next Claude session in
  the worktree loads project settings and runs those hooks outside any sandbox.
- **High: Unix sockets under the host `/tmp`.** The Implementer's Bash sees `/tmp`; sockets there
  that are not denied (the browser extension's bridge, which takes tool requests without
  authentication, other sessions' proxy bridges) are reachable. Proven in a copy of the sandbox
  setup.
- **High: a link swap between the file guard's check and the CLI's write** sends a write out of the
  worktree (proven with the steps forced in order; the live race was not tested).
- **Medium:** changes made after the last review (by the test run or the MR-text turn) reach the
  commit; the gate's outer wrapper shares the host network namespace (X11 without a cookie);
  a handed-over branch is live in the user's checkout before anyone reads it.
- **Held:** the secret files and `/run` stayed hidden; the test sandbox has no network and its
  processes end at the timeout; Codex's own sandbox blocks Unix sockets; project settings cannot
  widen Claude's sandbox; the factory's Git runs no hooks or fsmonitor; the reaper ends only the
  factory's own leftovers.

### 2. Attack surfaces outside the sandbox

- The dashboard, the remote dashboard and the MCP endpoint kept every protection through the
  refactor (Host and Origin checks, token or cookie, the remote login gate, typed confirmation).
- **High: the GitLab token can go to the wrong host.** Since SF-153 the hourly logins check, like
  the merge request code, treats every host that is not GitHub or one of four known others as
  GitLab, and sends the GitLab token there when `SF_GITLAB_URL` is not set. With today's
  workspaces it goes only to the right host; a workspace on another forge would receive it.
- **Medium:** the MCP `read_file` tool returns git-ignored secret files (`.envrc`, `*.pem`) to
  ChatGPT; the guard reads text diffs only, so a binary or `-diff` file goes through unscanned; the
  digest's Claude session has no MCP lockdown; the automatic hand-over brings agent-written build
  and IDE files into the checkout the IDE watches.
- **Low:** a planner that is talked into it can queue unattended jobs; each health pass logs a
  refused request; notifications send ticket names to the configured ntfy server; child processes
  inherit the env file's other values; push errors are not masked; the remote typed confirmation is
  the key the screen shows.

### 3. Code after the refactor

- Gains: the command, route and stop tables, typed page code, the strict compiler, the comment
  rule.
- Still wrong: job-state sets are written in about seven places; the web payload types are a hand
  copy of the server's; execution's seven parts call each other both ways; `startDashboard` is one
  1,040-line closure; the page code is ten scripts in one global namespace; the size ratchet was
  raised by hand the day it landed and counts lines, not size; the client tests run against an
  877-line fake DOM; `catch {}` hides failures in about 146 places.

### 4. Reliability and process

- **Nothing outside `sf serve` watches it.** A crash loop (as on this day, about 33 restarts in 10
  minutes) is silent; the unit restarts forever with no limit and no `OnFailure=`.
- **The install builds in place:** `npm run build` deletes `dist/` first, so a failed build leaves
  the service unable to start.
- **The merged code is never the tested code.** Tests run before the rebase; nothing tests the
  merge result; hand-made pull requests get no tests. Two green tickets broke main this day.
- **Plan checks go stale only when the Task text changes**, never when the code does; a failed check
  holds the queue until someone notices (the 7-hour stall).
- Laptop suspend stretched the test timer for 7 hours; the run limit's CPU is shared with the rest
  of the factory; a refactor Task's wording deleted a file; folder scopes without `/**` produced
  false findings. Most of the rework came from Task rules, not Task length.
