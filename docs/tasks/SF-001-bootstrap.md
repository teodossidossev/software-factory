## 4. Какво да имплементираш

### 4.1. Минимален TypeScript проект

Създай само файловете, нужни за работещия bridge, проверките и кратката документация. Използвай bridge/ за имплементацията, освен ако съществуващата структура изисква друго.

Осигури документирани команди за:

- MCP smoke проверка.

Запази lockfile. Избягвай празни директории за бъдещи компоненти, втори package manager, излишни слоеве и placeholder services.

Стил на JavaScript/TypeScript:
- const, когато стойността не се преназначава;
- никога var;
- точка и запетая;
- фигурни скоби след всяко if;
- всички code comments на английски.

### 4.2. Локален MCP server

Използвай официалния MCP SDK и Streamable HTTP transport. Не пиши собствен MCP/JSON-RPC transport.

Server-ът:
- има стабилни име и версия;
- слуша само на 127.0.0.1;
- използва /mcp;
- има конфигурируем порт, например 8787, и ясна грешка при зает порт;
- поддържа чисто спиране и освобождаване на своя listener;
- използва приложимите SDK защити за Host/Origin при локален HTTP server;
- не отваря публичен тунел, LAN listener или permissive CORS;
- не извиква платен LLM API.

Може да добавиш минимален /health endpoint за готовността на локалния процес. MCP функционалността трябва да се провери през MCP client.

### 4.3. Три тесни MCP tools

Имената по-долу са предложен договор за тази итерация. Адаптирай ги само ако съществуваща проектна конвенция го налага и документирай промяната.

**factory_status**
- Без входни аргументи.
- Връща име и версия на bridge-а и ясно показва local-only pilot режима.
- Не връща secrets, пълна environment информация или произволни файлове.

**factory_write_probe**
- Приема един аргумент message: непразен string с максимум 4096 символа.
- Записва съобщението като един фиксиран UTF-8 пробен артефакт в runtime директорията.
- Връща проверим резултат за запазеното съдържание.
- Повторен запис заменя само този пробен артефакт; това поведение трябва да е описано в tool metadata.
- Не приема произволен filepath, shell command, repository URL или session ID.
- Невалидният вход се отхвърля преди промяна на файла.

**factory_read_probe**
- Без входни аргументи.
- Прочита точно същия фиксиран артефакт.
- Връща съдържанието или ясен структуриран резултат, че още няма запис.

Дефинирай точни input/output schemas и коректни tool annotations за реалното поведение. Използвай минималния transport/session режим, който официалният SDK поддържа за тези операции.

### 4.4. Съхранение

Използвай изрично определена runtime директория, например чрез FACTORY_DATA_DIR. За локалния пилот е допустима ясно документирана factory-data директория под project root, изключена от Git.

MCP tool callers не могат да избират файлов път. Записът трябва да оставя завършен артефакт и да се запазва след рестарт на server-а. Използвай прост безопасен файлов запис, без отделна база данни.

Това е обхват на MCP инструментите. Не променяй filesystem permissions или sandbox настройките на Claude Code.

Направи един кратък integration/smoke сценарий с официален MCP client. Той трябва да стартира свой server на свободен loopback порт и да използва собствена временна runtime директория, за да не презаписва ръчна проба на потребителя.

Тестовият сценарий трябва да почиства собствените си процеси и временни данни. Не спирай други процеси при зает порт.

### R1 — Обработване на невалиден HTTP request target

Приоритет: P2, задължителна runtime корекция.

Място: /home/teo/IdeaProjects/software-factory/bridge/src/server.ts, ред 139 в предоставения snapshot.

HTTP request callback-ът подава req.url на new URL(...), преди да извика MCP handler-а. Това изпълнение няма обработка на изключението.

Request targets като // и //[ предизвикват ERR_INVALID_URL. С разрешен Host 127.0.0.1:<port> и без Origin заявката преминава проверките на заглавките и достига този ред. Необработеното изключение може да прекрати bridge процеса.

Проверка на конкретния URL израз в наличния Node v24.22.1:
- // → ERR_INVALID_URL
- //[ → ERR_INVALID_URL
- /mcp → /mcp

Това е установен проблем в parsing пътя, подкрепен от статичния преглед. Пълната HTTP репродукция върху реалния bridge трябва да се направи в Claude средата; опитът за локален HTTP harness в средата на ревюто беше ограничен от listen EPERM. Не представяй тази тясна проверка като повторно изпълнен smoke suite.

#### Очакван резултат

Обработи невалидния request target на HTTP границата. Непарсваща се заявка трябва да получи HTTP 400, а процесът да продължи да обслужва. Използвай минимална промяна, съвместима с настоящия routing и официалния MCP handler.

#### Критерии за приемане

1. Regression проверката изпраща точния проблемен request target към собствен тестов bridge процес на свободен loopback порт; клиентът не трябва да нормализира target-а предварително.
2. Проверява HTTP 400.
3. След това през истински MCP client извиква factory_status и получава очаквания резултат от същия процес.
4. Показва, че пробният артефакт не е променен от невалидната заявка.
5. Съществуващите Host/Origin проверки и /mcp поведението продължават да работят.

Един тесен regression сценарий е достатъчен. Не добавяй нов HTTP framework или общ error-handling framework за тази поправка.

### O1 — Незадължително: ограничено изчакване в smoke harness-а

Място: /home/teo/IdeaProjects/software-factory/bridge/test/smoke.test.ts, spawnBridge(), stopBridge() и after().

В момента startup и shutdown изчакванията нямат краен срок. Ако бъдеща регресия остави child процеса жив, но без READY или без приключване след SIGTERM, smoke командата може да чака безкрайно. При приключване по сигнал exitCode може да е null; signalCode също е релевантен. Cleanup изпраща SIGKILL, но не изчаква приключването преди изтриване на временната директория.

Подходящо бъдещо подобрение е ограничено изчакване, коректна обработка на вече приключил child и изчакване на собствените процеси при cleanup. Това не обезсилва успешните настоящи проверки и не е отделен blocker за SF-001. Не разширявай текущата корекция само за да го изпълниш.
