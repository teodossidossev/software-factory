## R1 — Обработване на невалиден HTTP request target

Приоритет: P2, задължителна runtime корекция.

Място: /home/teo/IdeaProjects/software-factory/bridge/src/server.ts, ред 139 в предоставения snapshot.

HTTP request callback-ът подава req.url на new URL(...), преди да извика MCP handler-а. Това изпълнение няма обработка на изключението.

Request targets като // и //[ предизвикват ERR_INVALID_URL. С разрешен Host 127.0.0.1:<port> и без Origin заявката преминава проверките на заглавките и достига този ред. Необработеното изключение може да прекрати bridge процеса.

Проверка на конкретния URL израз в наличния Node v24.22.1:
- // → ERR_INVALID_URL
- //[ → ERR_INVALID_URL
- /mcp → /mcp

Това е установен проблем в parsing пътя, подкрепен от статичния преглед. Пълната HTTP репродукция върху реалния bridge трябва да се направи в Claude средата; опитът за локален HTTP harness в средата на ревюто беше ограничен от listen EPERM. Не представяй тази тясна проверка като повторно изпълнен smoke suite.

### Очакван резултат

Обработи невалидния request target на HTTP границата. Непарсваща се заявка трябва да получи HTTP 400, а процесът да продължи да обслужва. Използвай минимална промяна, съвместима с настоящия routing и официалния MCP handler.

### Критерии за приемане

1. Regression проверката изпраща точния проблемен request target към собствен тестов bridge процес на свободен loopback порт; клиентът не трябва да нормализира target-а предварително.
2. Проверява HTTP 400.
3. След това през истински MCP client извиква factory_status и получава очаквания резултат от същия процес.
4. Показва, че пробният артефакт не е променен от невалидната заявка.
5. Съществуващите Host/Origin проверки и /mcp поведението продължават да работят.

Един тесен regression сценарий е достатъчен. Не добавяй нов HTTP framework или общ error-handling framework за тази поправка.

Източници:
- Node URL constructor: https://nodejs.org/api/url.html#new-urlinput-base
- SDK Host guard: https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/node/middleware/hostHeaderValidation.html
- SDK Origin guard: https://ts.sdk.modelcontextprotocol.io/v2/api/@modelcontextprotocol/node/middleware/originValidation.html

## R2 — Поправка на обяснението за outputSchema

Приоритет: поправка на документацията.

Място: /home/teo/IdeaProjects/software-factory/docs/reports/SF-001-report.md, ред 145 в предоставения snapshot.

Обяснението, че MCP изисква outputSchema да има object root, не е общовалидно за използваните SDK v2 и протокол 2026-07-28. Официалното migration ръководство описва премахване на това ограничение и адаптиране към клиенти от 2025 ерата.

Сегашната схема с optional полета може да остане за SF-001. Handler-ите връщат пълните данни при exists=true и няма показан runtime дефект в този резултат. Коригирай отчета: това е опростен договор на пилота, а не обща невъзможност на MCP.

Не променяй автоматично схемата към discriminated union. Ако такава промяна бъде нужна по-късно, първо трябва да се провери как влияе на двата поддържани wire формата.

В същата секция уточни, че ограничението за тунели е обхват на SF-001; свързването чрез подходящ транспорт е планирана работа за SF-002. Не е необходимо предварително да се разширяват Host/Origin guards: реалните заглавки трябва да се проверят с избрания транспорт.

Критерий за приемане: отчетът описва действителния избор и границите на провереното поведение, без остарялото общо твърдение.

Източник:
https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2
Секция: JSON Schema 2020-12 posture (SEP-1613, SEP-2106).

## O1 — Незадължително: ограничено изчакване в smoke harness-а

Място: /home/teo/IdeaProjects/software-factory/bridge/test/smoke.test.ts, spawnBridge(), stopBridge() и after().

В момента startup и shutdown изчакванията нямат краен срок. Ако бъдеща регресия остави child процеса жив, но без READY или без приключване след SIGTERM, smoke командата може да чака безкрайно. При приключване по сигнал exitCode може да е null; signalCode също е релевантен. Cleanup изпраща SIGKILL, но не изчаква приключването преди изтриване на временната директория.

Подходящо бъдещо подобрение е ограничено изчакване, коректна обработка на вече приключил child и изчакване на собствените процеси при cleanup. Това не обезсилва успешните настоящи проверки и не е отделен blocker за SF-001. Не разширявай текущата корекция само за да го изпълниш.
