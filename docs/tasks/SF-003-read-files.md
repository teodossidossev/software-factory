## 3. Repository root и файлов достъп

Root се избира локално при стартиране, с `FACTORY_REPO_ROOT` и разумна стойност по подразбиране: коренът на checkout-а, в който се намира bridge-ът. Default-ът трябва да работи независимо от текущата shell директория. Следвай съществуващия подход към пътищата, но не извеждай repo root от `FACTORY_DATA_DIR` и не hardcode-вай потребителското home.

Разреши реалния root при стартиране и провери, че е съществуваща директория. При невалидна конфигурация дай ясна грешка, без тих fallback към друга директория. MCP caller-ът не може да подава или сменя root.

Правила за `path`:

- Непразен относителен Linux път с `/`; без NUL, backslash, абсолютен път или сегмент `..`. Не изпълнявай shell expansion или URL decoding.
- Разрешеният реален път трябва да остане вътре в realpath на root. Проверявай границата по path сегменти, а не с обикновен string prefix.
- Symlink е допустим само към разрешен файл вътре в root. Провери правилата и за подадения, и за крайния реален път.
- Чети само обикновени файлове. Директории, sockets, FIFOs и устройства получават ясна грешка.
- Допускай tracked, untracked и ignored файлове. Особено важно: `review/**` трябва да се чете. Не използвай `.gitignore` или `git ls-files` като общ филтър.

Минимални изключения за този инструмент: всеки `.git` сегмент; `.env` и `.env.*`, с изключение на `.env.example`, `.env.sample` и `.env.template`; точните имена `.npmrc`, `.netrc`, `.git-credentials`, `id_rsa`, `id_ed25519`; файлове с разширение `.key`, `.p12` или `.pfx`. Проверявай тези правила и през symlink alias. `.gitignore`, source файловете, lockfile-ът и `config/tunnel-client/software-factory.example.yaml` са допустими.

Runtime ключът и реалният tunnel-client профил остават извън repository-то и извън този достъп. Не логвай съдържанието на прочетените файлове. Не маскирай съдържание чрез автоматична подмяна във върнатия текст: ревюто трябва да получава точните байтове. Списъкът с изключения не е универсален детектор на тайни; не копирай истински credentials в source, примери или review пакети.

Това е договорът на MCP инструмента за едно repository. Не се променят OS правата на Claude. Не изграждай отделна filesystem платформа или защита срещу злонамерен локален процес, който състезателно подменя файлове.

## 4. Договор на factory_read_file

Входът е строг обект; непознати полета се отхвърлят.

| Поле | Значение |
| --- | --- |
| `path` | Задължителен относителен път в repository-то; максимум 4096 знака. |
| `offset` | Незадължителен цял byte offset, default `0`; от `0` до размера на файла включително. |
| `max_bytes` | Незадължителен цял размер на страница: default `16384`, minimum `4`, maximum `32768`. |

Успешният резултат има изрична output schema и еднакви стойности в `structuredContent` и съответния JSON text result:

| Поле | Значение |
| --- | --- |
| `path` | Нормализиран относителен път на заявения файл; без абсолютен host път. |
| `encoding` | Винаги `utf-8`. |
| `bytes` | Броят оригинални байтове на целия прочетен файл. |
| `sha256` | SHA-256 на същите оригинални байтове на целия файл; lowercase hex. |
| `offset` | Началният byte offset на тази страница. |
| `returned_bytes` | Броят оригинални байтове в тази страница. |
| `text` | Точният UTF-8 текст на страницата. |
| `next_offset` | `offset + returned_bytes`, ако има още съдържание; иначе `null`. |

Използвай MCP annotations `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false`. Опиши инструмента като четене на repository съдържание за ревю; обясни byte offsets, лимитите и използването на `next_offset`. Следвай API-то на вече инсталирания SDK v2, без миграция по пример от друга SDK версия. [2]

### Точност и четене на части

- Максимум 2 MiB за целия файл в тази итерация. Над лимита върни ясна грешка. Прилага се ограничено четене; само предварителен `stat` не трябва да води до неограничено зареждане на нарастващ файл.
- Валидирай като UTF-8 без загубна подмяна на невалидни последователности; текст с NUL се отхвърля като неподдържано съдържание.
- Запази LF/CRLF, евентуалния UTF-8 BOM и липсата или наличието на финален newline. Не trim-вай, не добавяй номера на редове и не форматирай съдържанието.
- Край на страницата е граница между UTF-8 символи. Никога не връщай разрязана кирилица или emoji; върнатите байтове са най-много `max_bytes`.
- Offset във вътрешността на UTF-8 символ или извън файла получава ясна грешка. При offset точно на EOF върни празен текст, `returned_bytes: 0`, `next_offset: null`. Празен файл се чете успешно.
- `bytes`, `sha256` и страницата се изчисляват от един и същ прочетен buffer. Hash-ът се връща на всяка страница. Ако файлът се промени между извикванията, ChatGPT сравнява hash-овете и започва четенето отначало; няма snapshot storage или cache.
- Това трябва да работи и за много дълъг единичен ред. Не превръщай line limit в пречка за пълен прочит.

За грешки при изпълнение използвай нормален MCP tool error (`isError: true`) със стабилен код и полезно кратко съобщение, съвместимо с SDK v2. Разграничи поне невалиден/забранен път, липсващ файл, неподдържан тип/съдържание, прекомерен размер, невалиден диапазон и грешка при четене. Вход, който не покрива input schema, може да бъде отхвърлен по стандартния начин на SDK; не добавяй transport обвивка само за уеднаквяване на грешките. Не връщай stack trace, секрети или абсолютни host пътища. Грешка при едно извикване не трябва да спира bridge-а.

## 5. Реализация и проверки

Предпочитана форма: един малък модул под `bridge/src/` за четенето и проверката на пътища; регистрация в съществуващия server; подаване на root от entry point. Запази transport кода и probe-store. Използвай Node стандартната библиотека и съществуващите dependencies.

Добави проверките в съществуващия тестов подход. Достатъчен е компактен набор върху временен repo root с фиктивно съдържание:

1. Успешен прочит на source файл, untracked файл и ignored `review/` артефакт, както и на примерния config. Точни text, bytes и SHA-256; поне един случай с български текст, emoji, CRLF и/или BOM.
2. Прочит на файл над един page limit, включително много дълъг ред и граница вътре в многобайтов символ. Последователните страници възстановяват оригиналните байтове без пропуск/дублиране и завършват с `next_offset: null`.
3. Празен файл, EOF и невалидни offset/max_bytes/непознати input полета; неподдържано UTF-8 съдържание и размер над лимита.
4. Отказ на absolute path, `..`, symlink извън root и sibling директория със сходен prefix. Разрешен вътрешен symlink и отказ на alias към забранен файл.
5. Отказ на `.git` и фиктивни credential файлове; липсващ файл и директория. Използвай fixtures, без четене на реални ключове от home.
