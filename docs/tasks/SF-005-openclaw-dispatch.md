## 1. Канонична структура

Оперативните данни са под:

```text
factory-data/
└── apps/
    └── <app-id>/
        ├── .env
        └── jobs/
            └── <job-id>/
                ├── instruction.md
                ├── dispatch.json
                └── openclaw-receipt.json
```

`.env` е специфичен за приложението и впоследствие ще съдържа локалния път към неговото repository.

Правила:

- `.env` не се показва и не се редактира от ChatGPT.
- ChatGPT използва `app-id`, никога абсолютен host път.
- Каноничната инструкция е `instruction.md` в медиатора.
- Всички operational данни остават извън Git.
- За SF-005 използвай отделен фиктивен pilot app-id, без реално application repository или необходимост от негов `.env`.

Не създавай глобален `.env` с пътища към приложенията.

## 2. MCP инструмент `factory_write_instruction`

Добави инструмент за запис на UTF-8 Markdown инструкция.

Вход:

- `app_id`
- `job_id`
- `content`
- `expected_sha256` — по избор, за актуализация

Поведение:

- При нов файл създава инструкцията.
- При съществуващ файл допуска промяна само при съвпадащ `expected_sha256`.
- Повторение със същото съдържание не създава нова версия или странични ефекти.
- Отхвърля невалидни идентификатори, traversal, symlink escape, NUL, прекомерен размер и непознати параметри.
- Записва атомарно и защитава от конкурентни обновявания.
- Връща пътя спрямо repository root, byte count и SHA-256.
- Не приема абсолютен filepath.
- Не записва код в application repository.
- Не изпълнява shell команди.
- Не задейства автоматично OpenClaw.

Съществуващият `factory_read_file` трябва да може да прочете записания `instruction.md` и да върне същото съдържание и SHA-256.

**Важна граница:** MCP инструментът не може самостоятелно да удостовери, че потребителят е дал одобрение в ChatGPT. Одобрението е задължителна стъпка в нашия workflow, а не неоснователно твърдение за криптографска проверка от bridge-а.

## 3. MCP инструмент `factory_request_dispatch`

Добави отделна операция за заявяване на изпращане.

Вход:

- `app_id`
- `job_id`
- `instruction_sha256`

Инструментът:

1. Намира единствено инструкция от контролираната operational директория.
2. Проверява точния SHA-256.
3. Създава устойчив `dispatch.json`, съдържащ идентификатор, версия и текущо състояние.
4. Не допуска повторно създаване на независимо изпълнение за същата заявка при retry.
5. Разграничава поне състоянията `requested`, `accepted` и `failed`.
6. Не връща `accepted`, преди да има доказателство от реален OpenClaw механизъм.

Инструментът не трябва да приема произволна команда, shell аргументи, директория или име на Docker контейнер.

ChatGPT ще го използва само след изрично потребителско разрешение за стартиране.

## 4. Минимален канал към OpenClaw

Запази работещия SF-004 Docker setup:

- `network_mode: none`;
- без публикувани портове;
- без host mounts;
- без Docker socket вътре в контейнера;
- без model API;
- без достъп до application repositories;
- без промени по Samba, home permissions или Docker daemon.

Проучи възможността за изпращане чрез предварително определена host-side операция, която използва `docker compose exec` и официалния OpenClaw CLI.

Провери конкретно OpenClaw 2026.10.7 за **native command automations**, които изпълняват фиксирана команда без модел.

Ако са налични:

- използвай строго ограничена native automation за приемане на тестовата заявка;
- предавай само `app_id`, `job_id`, SHA-256 и уникален request ID;
- не предавай Markdown съдържанието като shell команда;
- фиксирай командата и не приемай произволни аргументи от MCP caller;
- потвърди приемането чрез реален OpenClaw резултат или run history;
- запиши `openclaw-receipt.json` в медиатора с correlation ID и действителния резултат;
- при повторна заявка не изпълнявай повторно същото действие;
- не докладвай успешна доставка само защото `docker exec` или `gateway health` са върнали exit 0.

Ако за това е необходимо тясно разрешаване на native automations в активната OpenClaw конфигурация, първо провери точния конфигурационен договор. Обнови само необходимите настройки и запази останалите ограничения от SF-004.

Не разрешавай общ `tools.exec` за агента, не включвай модел и не активирай Control UI.

**Важно:** command automations са административен execution механизъм. Не излагай възможността за създаване на произволни automation команди като MCP инструмент.

Ако инсталираната версия не поддържа необходимия механизъм или изисква неподготвени права, не го имитирай със собствен scheduler. Завърши записването и устойчивата dispatch заявка, а интеграционния blocker документирай с конкретни доказателства.

## 5. Контрол на изпълнението

Използвай минималните необходими скриптове за механичното предаване.

Не създавай собствен workflow engine, постоянен polling daemon, task database или dashboard.

Bridge-ът трябва да предоставя само точно определени операции. Ако е необходим host-side relay, той трябва да използва фиксирани команди и валидирани идентификатори, без общ shell execution интерфейс.

Разграничавай:

- `stored` — инструкцията е записана;
- `requested` — заявено е изпращане;
- `accepted` — OpenClaw реално е потвърдил приемането;
- `completed` — бъдещо изпълнение е приключило.

Не използвай `completed` в този pilot само защото сигналът е приет.

## 6. Проверки

Провери с реалния MCP client и съществуващия тестов подход:

1. Създаване и прочитане на Markdown инструкция на кирилица.
2. Идентични bytes и SHA-256 при запис и прочитане.
3. Успешна редакция с правилен предишен SHA-256.
4. Отказ при остарял SHA-256, без загуба на съдържание.
5. Отказ при невалидни идентификатори и опасни пътища.
6. Записът не стартира OpenClaw.
7. Dispatch на несъществуваща или променена инструкция се отхвърля.
8. Повторна заявка не води до дублиране.
9. Реално OpenClaw потвърждение за фиктивен job, ако native механизмът е достъпен.
10. Грешка на OpenClaw не се представя като успех.
11. Съществуващите MCP инструменти, Host/Origin защитите и тунелът остават работещи.
12. Няма промени в Git index-а или application repository.

Приеми отчетените успешни SF-004 проверки. Повтаряй само проверките, засегнати от новите промени.
